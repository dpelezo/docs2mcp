# Agent eval

Do agents finish more tasks with docs2mcp's task-shaped tools than with a direct conversion? This eval answers that. The plan and its reasons are in [ADR 0013](../../docs/adr/0013-agent-eval.md).

**Status:** complete for Week 3. The first full run on `claude-haiku-5-5` is below (#51).

## Results (2026-11-25, `claude-haiku-5-5`)

**Short version:** on the three APIs every condition covers, docs2mcp's task-shaped tools (C) succeeded slightly more often than the official-OpenAPI conversion (A), 98.3% against 95.0%, and used 22% fewer tokens. On complex tasks the gap was bigger: 100% against 83%. FastMCP on the same files (D) was the weakest and the most expensive. But C did **not** beat docs2mcp's own direct design (B) across all six APIs: B 95.7%, C 94.7%. Most tasks were easy enough that every condition solved them, so the differences rest on a few tasks.

| On PokéAPI, Frankfurter and Postcodes.io | Runs | Success (min / mean over repeats) | Grounded success | Tool calls | Tokens per task | Cost per task |
|---|---|---|---|---|---|---|
| A: OpenAPI file, docs2mcp's converter | 180 | 93.3% / 95.0% | 95.0% | 1.73 | 33,511 | $0.0035 |
| B: docs2mcp, one tool per endpoint | 180 | 96.7% / 97.8% | 97.8% | 1.76 | 29,228 | $0.0031 |
| C: docs2mcp, task-shaped | 180 | 98.3% / 98.3% | 98.3% | 1.61 | 26,065 | $0.0027 |
| D: FastMCP `from_openapi` (one repeat) | 60 | 90.0% | 83.3% | 3.48 | 69,663 | $0.0072 |

| Complex tasks, same APIs | A | B | C | D |
|---|---|---|---|---|
| Success | 83% | 97% | 100% | 75% |

Across all six APIs, B and C are level. C is ahead on PokéAPI (100% against 98.3%, with 16% fewer tokens), level on four APIs, and behind on Open Library (78% against 85%, with 67% more tokens).

Full tables, by API and level, and every failed run: [`results/2026-11-25-haiku/report.md`](results/2026-11-25-haiku/report.md), generated by `scripts/agent_report.py` from the committed `results.jsonl`.

### What the failures were

- **Real tool-design differences:**
  - **Condition A on postcodes_io-019 (3 of 3 wrong):** the official file has no place search, so the agent guessed nearby postcodes.
  - **Conditions A and D on frankfurter-018:** the official file's tools didn't lead the agent to the European Central Bank's own rates. It answered with the blended rate.
  - **Condition C on open_library-005 (3 of 3 failed):** the task-shaped design has no route to an edition's page count. That is a gap in Haiku's design, which was approved without review.
- **FastMCP's output schemas (condition D):** the official Postcodes.io file declares `integer` and `string` where real responses hold `null`. The MCP client rejects those results, so the agent fell back to the few tools that still worked. That cost 7.5 tool calls per task and a 60% grounded success rate on Postcodes.io. D also sends whole PokéAPI responses, about 170,000 tokens per task.
- **The agent, in every condition:**
  - **postcodes_io-014 (no answer in 8 of 9 runs):** after fetching both postcodes, the agent worked out the distance in its reply and never called `submit_answer`.
  - **pokeapi-017 (2 runs):** wrong type matchups.
- **The tasks or the scoring.** These are counted as failures here, and a correction would go in its own pull request and be re-scored on these same outputs:
  - **open_library-017:** the right answer with extra words, "Things Fall Apart (1958)", which the `exact` rule fails (5 runs). open_library-015 has the same problem in 1 run.
  - **open_library-020 (6 of 6):** "the top result" depends on the search. A free-text search puts *The Fellowship of the Ring* (OL27513W) first, and a title and author search puts *The Lord of the Rings* (OL27448W) first.
  - **open_library-016 (6 runs):** the Books API and the search index disagree about which edition has the ISBN.
- **Answers from memory:** open_meteo-003 ("km/h") was answered correctly in all 6 runs without a single tool call. It counts as a pass but not a grounded one. That is what the grounded metric is for (#57).

### Bugs the eval found

The pilots and the full run turned up four problems in what docs2mcp generates or in the baselines, all found before any result was claimed:

1. **The 20,000-character limit hid PokéAPI's stats and types** in every condition. Long lists and objects are now shortened first (#58).
2. **Routes dropped arguments silently:** Frankfurter's date was lost when base and quote were also given. The server now picks the route that takes the most arguments, and names any it leaves out (#63).
3. **The runner ended a run when the MCP client rejected a tool result.** That happened with FastMCP, whose results don't match the official file's response schemas. Now the agent gets the rejection as a tool error and carries on, as it would in an MCP host (#64).
4. **Open Library's `/isbn/` endpoint answers with a 302 redirect, which generated servers do not follow.** So the agent gets an empty body. This is likely behind 10 of the 22 Open Library failures in B and C (open_library-004, -005 and -016). The other 12 are the scoring and task problems above. It was fixed after this run (#68, PR #70), so these numbers still include it. The run was not repeated.

### Limits

- **One model, Haiku.** Larger models may close or widen the gaps.
- **Small differences:** most tasks were solved by every condition, so the comparison rests on a handful of tasks. A and C differ by 6 runs out of 180.
- **Conditions B and C were approved as generated,** without the human review docs2mcp expects. C's Open Library gap would probably have been caught in review.
- **Condition D ran once,** by choice, because of its PokéAPI token cost.
- **Two code versions:** 622 runs used commit `bbb81b8`. The 218 runs retried after a rate limit and a credit stop (`errored.jsonl`) used `12c4762`, which only adds `--retry-errors`. The retried runs used 2 concurrent tasks instead of 4.
- **Cost:** $2.62 in model calls for the 840 scored runs.

## Task files

Tasks are hand-written TOML, one file per API, in `tasks/<api>.toml`. The schema is [`docs/tasks.schema.json`](../../docs/tasks.schema.json), generated from `src/docs2mcp/evals/tasks.py`.

```toml
api = "frankfurter"

[[task]]
id = "frankfurter-001"
level = "single"
question = "What was the EUR to USD exchange rate on 2024-01-15?"
evidence = "GET https://api.frankfurter.dev/v2/rate/EUR/USD?date=2024-01-15"
answer = { rule = "number", value = 1.0945, abs_tolerance = 0.0001 }
```

| Field | Meaning |
|---|---|
| `id` | `<api>-NNN`, unique in the file |
| `level` | `single` (one call), `multi` (two or three calls, or the right options), `complex` (several steps or an unusual parameter) |
| `question` | What the agent is asked, word for word |
| `evidence` | How the expected answer was checked, usually the request that returns it |
| `answer` | The scoring rule (below) |
| `grounding` | `literal` (default): the answer is a value in an API response. `derived`: it is worked out, such as a sum, count, conversion, mean, or yes or no. |
| `note` | Optional, for reviewers. The agent never sees it. |

Every answer must be stable: a past date, a fixed record, never "today".

## Scoring rules

The agent submits one answer as text. No model judges it.

| `rule` | Fields | Passes when |
|---|---|---|
| `exact` | `value`, `accept` (other answers that count), `case_sensitive` | The trimmed, space-collapsed and (by default) case-folded answer equals `value` or one of `accept` |
| `number` | `value`, `abs_tolerance`, `rel_tolerance` | The first number in the answer is within `abs_tolerance + rel_tolerance × \|value\|`. Thousands separators are allowed. |
| `contains` | `value` (a list), `case_sensitive` | The answer contains every string in `value` |
| `set` | `value` (a list), `case_sensitive` | The answer, split at commas, semicolons or new lines, is exactly that set, in any order |

Choices that keep answers stable:
- **Frankfurter:** every task asks for European Central Bank rates. By default the API blends several providers, and that blend can change when a provider is added.
- **Open-Meteo forecast:** no task asks for a weather value, because those change with every model run. Tasks ask about elevation, time zone, units and how many values a request returns.
- **Postcodes.io:** tasks avoid counts of postcodes, which change as postcodes are added and terminated.

Every expected answer was checked on 2026-11-24 against the live responses (`scripts/fetch_evidence.py`, below). 87 answers appear word for word in a response. The other 13 are worked out from one, such as a sum, a conversion, a count or a yes or no. Their `note` shows the working where it isn't obvious.

## Grounded success

A correct answer can come from the model's memory instead of the tools. In the pilot, Haiku answered pokeapi-007 (Jolteon's Speed, 130) correctly in every condition, although the server had cut the response 300,000 characters before `stats`. So each run also checks whether a literal answer appears in a tool result the agent saw, using the task's own rule. For `number`, any number within the tolerance counts. The report shows **grounded success** next to success.

- **Literal tasks:** 83 of the 100. Each one's expected answer was checked against its own recorded evidence, and all 83 are found there.
- **Derived tasks:** 17. They are not checked, because the answer is not in any response. Two of them (open_meteo-012's 6 and postcodes_io-012's "no") would match by chance.
- **Known gap:** a grounded number can still be a coincidence, so the check can only lower a score, never raise one.

## Condition A: the official OpenAPI files

Condition A is what other generators make: one tool per operation in the API's own OpenAPI file, approved without review. `src/docs2mcp/openapi.py` converts the file into docs2mcp's spec, and the same direct design and server template as condition B build the server. So A and B differ only in where the spec came from, and A and C only in the tools.

| API | Tools | Tool list (tokens) | What the official file leaves out |
|---|---|---|---|
| PokéAPI | 102 | ~12,400 | nothing the extraction reference has |
| Frankfurter | 9 | ~2,300 | nothing the extraction reference has |
| Postcodes.io | 11 | ~1,900 | 3 routes (autocomplete, outcode reverse geocoding, nearest outcodes), 12 parameters (such as `radius` and `limit` on nearest postcodes and `q` on places), and the bulk lookup's request body |

The designs are committed in [`conditions/openapi/`](conditions/openapi/): `spec.json`, `tools.json`, and `source.json` with the file's URL, SHA-256 and every part that could not be converted. Rebuild them, and then a server, with:

```bash
uv run python -m scripts.openapi_condition
uv run docs2mcp generate evals/agent/conditions/openapi/postcodes_io/tools.json \
    --spec evals/agent/conditions/openapi/postcodes_io/spec.json --out servers/openapi/postcodes_io
```

The Postcodes.io gaps take away the direct route for some tasks in condition A: 009 (needs `radius`), 010 (autocomplete), 013 and 019 (place search) and 016 (nearest outcodes). 015 and 017 need one lookup per postcode instead of a bulk request. That is part of what the eval measures: documentation can say more than the official file.

## Condition D: FastMCP from the same file

Condition D is [FastMCP](https://gofastmcp.com)'s `from_openapi`, run on the same official OpenAPI file as condition A, with FastMCP's defaults. `scripts/fastmcp_server.py` changes nothing but the HTTP client's transport, which uses the same cassette as A, B and C (FastMCP uses `httpx2`, so the cassette is wrapped in an `httpx2` transport, with the same request keys).

| | A (docs2mcp converter) | D (FastMCP) |
|---|---|---|
| Tools | one per operation | one per operation |
| Tool list (PokéAPI) | ~12,400 tokens | ~12,800 tokens |
| Long responses | biggest lists halved to fit 20,000 characters, with a note (#58) | returned whole |
| Errors | `returned HTTP 4xx`, schema validation | `HTTP error 4xx`, `Missing required arguments` |

Both kinds of error text count as invalid calls. The original files and their licenses are in `conditions/openapi/<api>/`.

## Running it

1. **Make condition C's designs** (Haiku, a few cents per API). The task design is made from the same extracted spec as condition B:

   ```bash
   for id in pokeapi frankfurter postcodes_io open_library open_meteo open_meteo_geocoding; do
     uv run docs2mcp design specs/$id/fix36/spec.json --model claude-haiku-5-5 \
       --out tools/$id/eval/tools.json --record tools/$id/eval/recordings
   done
   ```

2. **Build the servers** listed in [`conditions.toml`](conditions.toml). This writes `servers/eval/<A|B|C>/<api>/`, plus `manifest.json` with the SHA-256 of every input. B and C approve every valid tool as generated, with no hand edits.

   ```bash
   uv run python -m scripts.build_eval_servers
   ```

3. **Run the agent.** Start with the pilot: 10 tasks in every condition, 32 runs (6 in A and 6 in D, 10 each in B and C). On Haiku, A, B and C cost about $0.08. D can cost more, because it sends whole PokéAPI responses. Then do the full run with 3 repeats.

   ```bash
   uv run python -m scripts.agent_eval --pilot --out runs/pilot
   uv run python -m scripts.agent_eval --repeats 3 --condition-repeats D=1 --out runs/full
   ```

`scripts/agent_eval.py` is a LangGraph graph with two nodes. `model` calls Claude with the server's tools plus `submit_answer`. `tools` calls the MCP server and stops when an answer is submitted or after 12 model calls. Every condition gets the same system prompt (`docs2mcp.evals.agent.SYSTEM_PROMPT`) and the same limits.
- **Output:** each run appends a line to `runs/<name>/results.jsonl` as it finishes, so a stopped run resumes where it left off. At the end it writes `summary.md` and `metrics.json`.
- **Tracing:** with Langfuse keys set, each task is one trace, with a span per model call and per tool call.
- **Repeats:** `--condition-repeats D=1` runs condition D once while the others run `--repeats` times. D sends whole PokéAPI responses, about 200,000 tokens per task, and the owner chose one run for it (2026-11-25).
- **Failed model calls:** a run ends in an error only when the model call itself fails, for example on a rate limit, no credit left or a network error. Those runs say nothing about the tools, so `--retry-errors` moves them to `errored.jsonl` and runs them again. Use it with the same `--out`.
- **Client-side failures:** if the MCP client rejects a tool result, the agent gets the failure as a tool error (outcome `error`) and can carry on, as it would in an MCP host. The run is not ended. In pilot 2, FastMCP's Postcodes.io tools returned results that didn't match their own output schema, and the client rejected them.
- **Invalid tool calls** are calls the server rejected for their arguments, either a schema validation error or an HTTP 4xx from the API. A "not recorded" error in replay mode is counted separately, because it is a problem with the run, not the tools.

## Recorded responses

Every eval server runs through `scripts/eval_server.py`. It loads the generated `server.py` unchanged and sets its `transport` hook to a cassette (`src/docs2mcp/evals/cassette.py`):

```bash
uv run python -m scripts.eval_server servers/openapi/frankfurter \
    --cassette recordings/agent/frankfurter.jsonl.gz --mode cache
```

| Mode | Recorded request | New request |
|---|---|---|
| `record` | asks the API again | asks the API and records |
| `cache` (default) | replays | asks the API and records |
| `replay` | replays | fails with a "not recorded" tool error |

- **One cassette per API**, shared by all three conditions, so the same request gets the same data whichever server makes it.
- **Matching:** requests match on method, URL with sorted query parameters, and JSON body.
- **No secrets:** headers are never stored, and query parameters whose name contains "key", "token" or "secret" are blanked.
- **Format:** gzip-compressed JSON Lines. A PokéAPI `/pokemon` response is about 370 KB of JSON.
- **Where they live:** `recordings/` is git-ignored, so cassettes stay on the machine that made them. Responses from the AGPL-licensed sites (Open Library, Open-Meteo) are never committed. Whether to commit the other three for CI replay is decided with the results (#51).
